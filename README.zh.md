# Chest Loader

原版风味、纯服务端、对原版客户端友好的地狱门区块加载器，装在箱子里不用建。

本文档也有 [English](README.md) 版本。

木箱或木桶里按规定摆好黑曜石、动力铁轨和矿车，这个容器所在的区块就会被加载住，加载范围和形状与地狱门加载器相同。摆放被破坏后加载随即撤销，加载状态跨重启保留。

## 特性

- 全用原版物品搭。加载器就是一圈黑曜石围着动力铁轨和矿车，放进普通木箱或木桶。没有自定义方块，没有自定义物品，也没有新配方要记。
- 加载范围和地狱门一致。等级 30，半径 3，7×7 区块，中心 3×3 实体刻，与地狱门加载器完全相同。玩家全部离开维度后，机器照样运转。
- 纯服务端，原版客户端也能进。客户端什么都不用装，自定义 ticket 类型不参与注册表同步。单人存档和专用服务器都能用。
- 跨重启保留，也能安全卸载。位置由 mod 自己存，世界加载时把加载加回去，不用重开容器，也不用进那个维度。卸载后原版的 ticket 存储里不留任何痕迹。
- 形状可配置。图案、物品、每格数量都写在配置里一张配方式网格中。可以定义多套图案，各自开关平移和镜像，每格设最小和最大数量。
- 任何改动都抓得到。开关容器时会判定，周期扫描还能抓到绕过回调的漏斗进出。同一区块里的多个加载箱按引用计数处理，大箱子两半各自独立判定。
- 随时远程启停。`/chestloader disable` 撤掉加载但保留记录，`/chestloader enable` 远程恢复，不用跑到那个区块去。两种状态都跨重启保留，这两条指令连同 `list` 只需要权限等级 1。

## 构建

```bash
./gradlew build
```

产物在 `build/libs/chestloader-0.1.0.jar`。`build` 会连测试一起跑。

## 测试

39 个 JUnit 用例覆盖形状判定、配置解析、ticket 等级换算、存档 codec 往返（含 disabled 集合及其向后兼容）和恢复时的未加载轮次计数。它们不起服务端，`./gradlew test` 一秒出结果。形状判定通过一个只暴露物品和数量的 `SlotView` 接口来测，因为 26.2 里 `ItemStack` 的 data components 要等数据包加载才绑定，纯 JUnit 造不出来。

9 个 GameTest 覆盖 JUnit 够不到的部分：mock 玩家开关容器时 mixin 是否真的触发、大箱子两半是否各自独立判定、带 data components 的物品是否照样算数，以及 enable、disable 两个状态转换和它们的 ticket 处理。用 `./gradlew runGameTest` 单独跑。它会起一个测试服务端，所以 `build.gradle` 里写了 `eula = true`。

`fabric.mod.json` 的 environment 填的是 `*`，单人存档和专用服务器都能用。填 `server` 的话单人游戏里内置服务端属于客户端环境，mod 不会加载。自定义 ticket 类型注册进 `BuiltInRegistries.TICKET_TYPE`，这个注册表没有 SYNCED 属性，不参与注册表同步，所以原版客户端仍然能连入装了本 mod 的服务器。

## 摆放形状

木箱和木桶都是 27 格，按 9 列 3 行排布。摆什么形状由配置里的 `patterns` 决定，下面是默认的一套：一个 4 列 3 行的黑曜石闭环，环内左边放动力铁轨，右边放矿车。

```
      0  1  2  3  4  5  6  7  8
行0   .  O  O  O  O  .  .  .  .
行1   .  O  R  M  O  .  .  .  .
行2   .  O  O  O  O  .  .  .  .
```

`O` 是黑曜石，每格至少 1 块。`R` 是动力铁轨，至少 4 节。`M` 是矿车，1 个。`.` 必须为空。

闭环周长正好 10 格，与最小地狱门框架的黑曜石数量相同。

框架可以整体水平平移，列偏移取 0 到 5，共 6 种合法摆法。行位置固定，因为这套图案就是 3 行高，占满了容器。默认打开的 `mirror` 让框架的左右镜像也算数，对这个对称的环来说，效果就是中间两格可以左矿车右铁轨。换形状、换物品、改每格数量都在配置里做，见下面的配置一节。

判定忽略 data components，改过名字或者带附魔的黑曜石照样算数。哭泣的黑曜石不算，普通铁轨、探测铁轨、充能铁轨也不算。

大箱子的两半各自独立判定，各自打各自的 ticket。

## 加载范围

自定义 ticket 的默认加载等级是 30，对应半径 3。等级从中心区块向外传播，每远离一格加 1，按切比雪夫距离算。结果是中心加一圈共 3×3 实体刻，外面一圈方块刻，再外面一圈边界，总共加载 7×7。原版传送门 ticket 就是等级 30 半径 3，两者形状完全一致。

| 等级 | 表现 |
| --- | --- |
| 31 及以下 | 全部机制可用 |
| 32 | 实体不生成也不处理但可访问，区块刻不执行 |
| 33 | 只能被读写，不运行任何机制 |
| 34 及以上 | 不加载 |

ticket 带 does load、does simulate、should keep dimension active 三个 flag。最后一个是必须的：每个维度有独立的空闲计时器，到 300 tick 时该维度会停止处理实体 tick、方块实体 tick、末影龙战斗和闪电，维度里存在任何带这个 flag 的 ticket 才会让计时器清零。少了它，玩家全部离开下界后，下界的加载器区块虽然在内存里，机器仍然会停。

## 检测时机

玩家打开和关闭容器时各判定一次。关闭时也判定，因为玩家可能刚刚把东西拿走。

漏斗抽走或塞入物品不触发上面的回调，而箱子把自己所在区块加载住之后也不会因为区块卸载而失效，所以还有一个周期扫描：每个维度每 `scanIntervalTicks` tick 遍历一次当前激活列表，重新判定，不通过就撤销。

容器被破坏时通过 `ServerBlockEntityEvents.BLOCK_ENTITY_UNLOAD` 立即撤销。服务器停止时清空全部 ticket。

同一个区块里有多个加载箱时，mod 按区块记引用计数，只在计数从 0 变 1 时加 ticket、从 1 变 0 时撤销。原版的 ticket 存储会把同一区块内类型和等级相同的 ticket 合并成一张，不记引用计数的话，撤销其中一个箱子会连带把另一个箱子的加载也撤掉。

disabled 状态的加载器不参与上面这一切。它的区块通常没有加载，没有东西可读，也不该对它记未加载轮次。开关它不会让它复活，只有 enable 指令可以。回调和扫描对它做的是机会性清理：只要它的区块碰巧可读、而容器里的图案已经没了（或容器本身没了），记录就被删掉并通知附近玩家。区块未加载期间被拆掉的容器，记录会一直留到下次有东西看到它为止，最晚是 enable 指令本身——它会在区块回来后检查图案，不符合就删记录。上面那条 `BLOCK_ENTITY_UNLOAD` 撤销故意跳过 disabled 位置：这个事件在普通区块卸载时也会触发，而区块卸载对 disabled 的加载器来说是家常便饭，不代表容器被破坏。

## 持久化

激活位置按维度存在 `dimensions/<命名空间>/<路径>/data/chestloader/loaders.dat`，内容是一串打包过的方块坐标。世界重新打开时 mod 从这里把 ticket 加回去，不需要玩家再开一次容器，也不需要玩家进入那个维度。

自定义 ticket 的 persist flag 是关着的，不走原版那套 ticket 存盘。原版的 ticket 按区块存，只有 `chunk_pos` 没有容器坐标，恢复出来的 ticket 认不回是哪个箱子打的，周期扫描、数量上限和区块引用计数就全都对不上了。

自己存位置还有一个好处，卸载 mod 是安全的。`chunk_tickets.dat` 里不会留下任何本 mod 的条目，`loaders.dat` 落在 `chestloader` 命名空间目录下，原版根本不会去读它。这一条实测过：激活两个加载器、停服、把存档复制出来用原版 26.2 服务端打开，没有任何报错，`forceload query` 两个维度都是空的。

恢复时先无条件把 ticket 加回去，不看容器内容。这是因为读容器需要区块已加载，而加载区块正是 ticket 的作用。复查挂在周期扫描上，扫描时先查该区块是否已加载，没加载就跳过本轮只记一次数，加载了再取方块实体做完整判定，不通过就撤销。不用固定延迟是为了避免区块加载被别的因素拖慢时误撤销。连续 10 轮扫描都读不到的位置会被撤销并写一条警告日志，避免脏数据永久占着一张 ticket。

恢复时还会做三项检查。超出 `maxLoadersPerDimension` 或 `maxLoadersTotal` 的部分直接丢弃并写日志，因为两次启动之间上限可能被调小。坐标落在世界边界或高度范围之外的直接丢弃。数据包定义的维度被移除时，那个维度的记录随维度目录一起不再被读取。

disabled 位置存在同一个文件里，用独立的 `disabled` 字段，同一个位置不会同时出现在两个集合中。启停功能之前的旧存档解码出来就是一个空的 disabled 集合。反过来降级到旧版 mod 时，旧版会忽略这个未知字段，disabled 记录被遗忘，但不会错误加载任何东西。恢复时 disabled 位置不加 ticket 也不挂复查，只做越界检查；数量上限对它不生效，因为上限约束的是实际加载的区块，而 disabled 的加载器什么都不加载。也因为这样，enable 时会重新检查上限，满了就失败并提示。

## 配置

文件在 `config/chestloader.json`，不存在时启动会写入默认值。

```json
{
  "patterns": [
    {
      "name": "obsidian-frame",
      "shape": [
        "OOOO",
        "ORMO",
        "OOOO"
      ],
      "keys": {
        "O": { "items": ["minecraft:obsidian"], "min": 1 },
        "R": { "items": ["minecraft:powered_rail"], "min": 4 },
        "M": {
          "items": [
            "minecraft:minecart",
            "minecraft:chest_minecart",
            "minecraft:hopper_minecart",
            "minecraft:furnace_minecart"
          ],
          "min": 1,
          "max": 1
        }
      },
      "slide": true,
      "mirror": true
    }
  ],
  "ticketLevel": 30,
  "scanIntervalTicks": 200,
  "maxLoadersPerDimension": 32,
  "maxLoadersTotal": 128,
  "notifyOnActivate": true,
  "particleOnActive": true
}
```

`patterns` 是一个列表，容器匹配其中任意一套就激活。每套里：

`shape` 是逐行画出的图案。`.` 或空格是必须留空的格，其他字符是 key。行数最多 3，列宽最多 9，各行等长。`keys` 把每个字符映射到一组物品加数量范围。`items` 里任意一个物品都满足这一格，`min` 是这一格最少放几个，默认 1，`max` 是最多几个，省略就是一组 64。数量是每格单独判定，不是全箱累加。`slide` 打开时图案可以停在容器里任何放得下的行列偏移，没盖到的格必须为空；关掉则固定在左上角。`mirror` 打开时图案的左右镜像也算数。

`items` 里查不到的物品会在启动日志里报警告并跳过。一个 key 的物品全部查不到，这套 pattern 整体作废并记日志。所有 pattern 都作废时，没有容器会被激活。想允许 TNT 矿车，把 `minecraft:tnt_minecart` 加进 `M` 的 `items` 即可，刷怪笼矿车和命令方块矿车不建议加，生存里拿不到。想换成别的形状、物品或数量，直接改 `shape`、`keys` 和 `min`/`max`。

`ticketLevel` 可以调，但 32 及以上会让中心区块失去实体刻。取值会被限制在 25 到 33 之间。

`maxLoadersPerDimension` 和 `maxLoadersTotal` 是数量上限。加载出来的区块里如果又有别的加载箱，会链式展开，没有上限时一条链能拖起大量区块。超过上限时拒绝激活，并给触发的玩家发一条聊天消息。

## 指令

```
/chestloader list
```

列出所有被跟踪的容器，enabled 和 disabled 都在内，按维度分组，同时显示 ticket 等级、半径和加载边长。重启或远程 enable 后还没复查过的位置会额外标出来，disabled 的位置标 `disabled`。聊天栏里每个条目末尾有一个可点击的 `[disable]` 或 `[enable]` 按钮，点击即执行对应指令；按钮里显式写了维度，跨维度也能用。控制台里按钮显示为纯文本。

```
/chestloader disable <x> <y> <z> [维度]
/chestloader enable <x> <y> <z> [维度]
```

`disable` 撤掉一个激活加载器的加载，但保留记录；容器原地不动，区块像普通区块一样卸载。如果同区块还有别的加载器，区块会继续保持加载，回复里会说明。`enable` 远程还给一个 disabled 加载器它的 ticket：区块不需要已加载，也不需要有人跑过去。读容器需要区块已加载，而加载区块正是 ticket 的作用，所以远程 enable 和重启恢复走同一套机制：先加 ticket，周期扫描等区块可读后做第一次检查，不符合就撤销。区块碰巧已经可读时当场检查，图案已经没了的话直接删掉记录。省略维度参数时在指令发送者所在维度执行。

`list`、`enable`、`disable` 需要 moderator 权限等级（1），受信任的玩家不用完整指令权限也能管理加载。`check` 驱动整条激活链路，保持 gamemaster 等级（2）。

```
/chestloader check <x> <y> <z>
```

对指定位置跑一次与开箱完全相同的判定，符合就激活，不符合就撤销。对 disabled 位置只报告状态，绝不激活。用来在不碰容器的前提下查一个位置的状态，也是唯一能从控制台驱动整条激活链路的入口，无头服务器上验证时用得到。

## 玩家反馈

激活时给打开容器的玩家发一条消息，说明该区块已进入强加载，并提醒这个容器不能再当储物箱用。失效时给附近 32 格内的玩家发一条消息。`particleOnActive` 打开时，激活的容器上方每秒生成少量 portal 粒子。

聊天消息是英文字面量，不走翻译键，任何客户端都能正常显示。

## 已知限制

加载不等于刷怪。只有中心在玩家 128 格以内的区块才执行区块刻，敌对生物在离所有玩家 128 格以外生成会立即消失。这个加载器带不动刷怪塔。

区块边界会截断一部分机制。流体和火焰扩散到方块刻区块之外的第一格会挂起，实体从实体刻区块走进方块刻区块会停住不动。机器要完整放在中心 3×3 的实体刻范围内。

激活的容器被这套形状占满，不能再存别的东西，也不能接漏斗输入。

重启后加载位置会立刻恢复，但复查要等到下一个扫描周期。这段时间里一个在离线期间被改坏的容器仍然占着 ticket，最长一个 `scanIntervalTicks`。远程 enable 有同样的窗口。

disabled 期间被拆掉的加载器，只要区块一直没加载就一直没人发现，`/chestloader list` 里可能挂着一条已经过时的 disabled 记录，直到下次有东西看到那个区块。记录一旦被删，在同一个容器里重新摆出图案就是一个全新的加载器，走正常的开箱判定激活；mod 不会记得它曾经被 disable 过。

## 验收方法

在加载区块里放一个自动机器，比如漏斗时钟带活塞，玩家走出加载范围后过几分钟回来，确认机器仍在运行。

在下界放一个加载器，所有玩家回主世界并等待超过 300 tick，确认下界的机器没有停。这一条专门验证 keep dimension active。

用 `F3` 加 `G` 观察区块边界，配合 `/chestloader list` 确认加载范围是 7×7。

从激活的容器里拿走一块黑曜石再关闭，确认加载被撤销。

用漏斗往激活的容器里塞一个物品，等待一个扫描周期，确认加载被撤销。

破坏激活的容器，确认加载被撤销且没有残留。

激活一个加载器后停服再重启，`/chestloader list` 应该立刻列出它并标注尚未复查，过一个扫描周期后标注消失。

在下界放一个加载器，重启后所有玩家都留在主世界，确认下界的机器继续运行。

停服后手动改坏容器内容再重启，确认过一个扫描周期后加载被撤销。

在 `/chestloader list` 里 disable 一个激活的加载器，走开后用 `F3` 加 `G` 确认区块卸载。重启服务器，确认它仍然列为 disabled。

人在另一个维度，点一个 disabled 加载器的 `[enable]`，等一个扫描周期，确认加载器旁的机器在没人过去的情况下恢复运转。

disable 一个加载器，在区块加载着的时候拆掉图案，确认记录从列表里消失。再试区块未加载的情况，确认记录一直留到 enable 时才被删掉。
